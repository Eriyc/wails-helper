# Wails Helper v0.1 Proposal

Status: Proposed  
Target: v0.1.0

## Purpose

Define a focused `v0.1` of `wails-helper` that removes repetitive app boilerplate while staying small and provider-driven.

This proposal prioritizes framework concerns that most desktop apps should not need to re-implement:

- error handling and recovery
- lifecycle and shutdown coordination
- window behavior policies
- config/state persistence
- task orchestration for background work

## Goals

1. Provide a stable core API for app shell concerns.
2. Keep all major integrations optional through interfaces/providers.
3. Offer sensible defaults and convenience helpers with minimal setup.
4. Preserve compatibility with custom Wails3 implementations.

## Non-Goals (v0.1)

- Building a full UI component library.
- Shipping concrete Wails3 runtime bindings for every platform detail.
- Implementing cloud telemetry backends.
- Adding advanced plugin/version negotiation systems.

## v0.1 Feature Set

### 1) Error System

Add a framework-level error model to standardize app-facing and user-facing failures.

Planned capabilities:

- typed error with code/category
- user-safe message and internal cause separation
- retryability marker
- wrapping and unwrapping helpers
- panic recovery helper for goroutines and event handlers
- optional bridge to `dialog.Manager` for user notifications

Expected API (draft):

```go
package helper

type ErrorCode string

const (
    ErrCodeUnknown       ErrorCode = "unknown"
    ErrCodeInvalidInput  ErrorCode = "invalid_input"
    ErrCodeUnavailable   ErrorCode = "unavailable"
    ErrCodeUnauthorized  ErrorCode = "unauthorized"
    ErrCodeConflict      ErrorCode = "conflict"
)

type AppError struct {
    Code        ErrorCode
    Message     string // safe for end users
    Cause       error  // internal detail
    Retryable   bool
    Metadata    map[string]string
}

func (e *AppError) Error() string
func Wrap(code ErrorCode, message string, cause error) *AppError
func IsCode(err error, code ErrorCode) bool
```

### 2) Lifecycle Manager

Provide ordered startup/shutdown hooks and cancellation handling.

Planned capabilities:

- register startup and shutdown callbacks
- deterministic shutdown order (reverse registration)
- context cancellation propagation
- timeout-aware shutdown
- panic-safe callback execution with error aggregation

Expected API (draft):

```go
package lifecycle

type Hook func(ctx context.Context) error

type Manager interface {
    OnStart(name string, hook Hook)
    OnStop(name string, hook Hook)
    Start(ctx context.Context) error
    Stop(ctx context.Context) error
}
```

### 3) Window Policy Layer

Build on `window.Manager` with reusable behavior policies.

Planned capabilities:

- named/singleton window registry
- open-or-focus semantics by key
- optional persisted geometry (size/position/state)
- main-window fallback helpers
- window close policy hooks (confirm/minimize-to-tray style decision point)

Expected API (draft):

```go
package windowpolicy

type OpenOrFocusOptions struct {
    Key     string
    Create  window.Options
}

type Manager interface {
    OpenOrFocus(ctx context.Context, opts OpenOrFocusOptions) (window.Window, error)
    SaveState(ctx context.Context, key string) error
    RestoreState(ctx context.Context, key string) error
}
```

### 4) Config + State Store

Add a small persistence abstraction for app settings and UI state.

Planned capabilities:

- key/value store interface
- JSON-backed default implementation
- atomic writes and safe read fallback
- schema version field for migration hooks

Expected API (draft):

```go
package state

type Store interface {
    Get(ctx context.Context, key string, dest any) error
    Set(ctx context.Context, key string, value any) error
    Delete(ctx context.Context, key string) error
}
```

### 5) Task Runner (Background Work)

Add cancelable background jobs with progress events.

Planned capabilities:

- start named tasks with context
- cancellation and cooperative shutdown
- progress reporting callback
- task state queries for UI binding

Expected API (draft):

```go
package tasks

type TaskFunc func(ctx context.Context, report func(percent float64, message string)) error

type Runner interface {
    Run(name string, fn TaskFunc) (taskID string, err error)
    Cancel(taskID string) error
    Status(taskID string) (TaskStatus, error)
}
```

## Existing Package Alignment

Current packages already provide a strong base for `v0.1`:

- `helper` as composition root
- `pkg/window` for window abstraction
- `pkg/dialog` for user interaction surface
- `pkg/events` for input/event handling
- `pkg/providers/autoupdate` and `pkg/providers/license` for external integrations

`v0.1` adds missing framework glue around these interfaces without changing their design intent.

## Backward Compatibility

- Keep existing interfaces source-compatible where possible.
- New functionality is additive.
- Existing `helper.Config` fields remain valid.
- Optional fields may be added for new managers (`LifecycleManager`, `StateStore`, `TaskRunner`, etc.).

## Milestones

### M1: Core Stabilization

- typed error model + helpers
- lifecycle manager package
- minimal tests for error and lifecycle behavior

### M2: Shell Behavior

- window policy manager
- state store with JSON backend
- helper integration points

### M3: Background Operations

- task runner with progress/cancel/status
- integration with auto-update and license refresh flows

### M4: Documentation + Examples

- update README with new quick-start
- add example app using v0.1 modules together

## Acceptance Criteria for v0.1.0

1. API docs and examples exist for all new modules.
2. Additive changes only; no breaking change to existing public interfaces.
3. Unit tests cover core behavior of errors, lifecycle, state, and tasks.
4. A single example demonstrates realistic integration.

## Open Questions

1. Should `state.Store` ship with encryption hooks in `v0.1` or defer to `v0.2`?
2. Should `windowpolicy` be in `pkg/window` as subpackage vs sibling package?
3. Should helper convenience methods expand in `v0.1` or stay minimal and let packages be used directly?
